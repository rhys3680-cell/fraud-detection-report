# 사기 탐지 정책 설계 보고서 — 기획서

> IEEE-CIS Fraud Detection 데이터를 활용한 **거래별 최적 대응 정책** 설계 및 비교 연구

---

## 1. 문제 정의

### 1.1 목적 진술

> 거래 발생 시점의 이용자·거래·기기·행동 맥락 데이터를 활용하여 사기 확률과 예상 피해
> 규모를 추정하고, 사기 피해 비용과 정상 거래 차단 비용의 균형을 고려해 거래별 최적
> 대응(승인·추가 인증·보류·차단)을 결정한다.

### 1.2 이 정의가 함의하는 것

본 연구는 사기 탐지를 **분류(classification) 문제가 아니라 결정(decision) 문제**로 다룬다.
목적 함수는 정확도나 AUC가 아니라 **총비용 최소화**이다.

```
총비용 = 놓친 사기 손실 + 정상 거래 차단 손실 + 검토 인건비 + 인증 마찰 비용
```

이 네 항은 서로 상충한다. 재현율을 올리면 정상 고객 차단이 늘고, 차단을 줄이면 사기
손실이 는다. 따라서 "최적"은 단일 지표의 최대화가 아니라 **비용 구조 위에서의 균형점**이다.

### 1.3 행동별 비용 구조

거래 $i$에 대해 사기 확률 $p_i$, 금액 $a_i$일 때 각 행동의 비용:

| 행동 | 사기일 때 | 정상일 때 |
|---|---|---|
| 승인 | $a_i + c_{cb}$ | $0$ |
| 추가 인증 | $s_f \cdot (a_i + c_{cb})$ | $(1-s_l)\cdot m \cdot a_i + c_{auth}$ |
| 보류 | $\approx 0$ | $c_{rev} + \delta$ |
| 차단 | $0$ | $m \cdot a_i + L$ |

기호:

| 기호 | 의미 |
|---|---|
| $c_{cb}$ | chargeback 처리 비용 |
| $s_f$ | 사기범의 추가 인증 통과 확률 |
| $s_l$ | 정상 고객의 추가 인증 통과 확률 |
| $m$ | 거래 마진율 |
| $L$ | 오차단으로 인한 고객 생애가치 손상 |
| $c_{rev}$ | 건당 검토 인건비 |
| $c_{auth}$, $\delta$ | 인증·지연 마찰 비용 |

최적 행동:

$$a_i^* = \arg\min_k \; p_i \cdot C_k^{fraud} + (1-p_i) \cdot C_k^{legit}$$

### 1.4 이 구조에서 따라오는 세 가지 귀결

1. **임계값은 튜닝 대상이 아니라 유도 결과다.** 위 식을 $p$에 대해 풀면 각 행동이 최적이
   되는 확률 구간이 자동으로 결정된다.

2. **임계값은 금액에 의존한다.** $L$과 $m\cdot a_i$가 금액에 비례하므로, 고액 거래는 더
   낮은 $p$에서도 차단이 정당화된다. 단일 cutoff는 원리적으로 차선이다.

3. **보류는 예산 제약 하의 할당 문제다.** 일일 검토 가능 건수 $B$가 유한하므로, 보류
   후보 중 "검토 시 절감액"이 큰 순으로 $B$건만 선택해야 한다.

4. **확률값의 절대 수준이 중요하다.** $p$가 기대비용 식에 숫자로 직접 들어가므로, 순위만
   맞고 값이 틀린 모델은 잘못된 결정을 내린다. → 캘리브레이션이 필수 (§4.3)

## 2. 데이터

### 2.1 IEEE-CIS Fraud Detection

- 출처: Kaggle 대회 (Vesta Corporation 실거래 데이터)
- 규모: 원본 약 1.3GB, train 약 59만 건
- 구성: `train_transaction` + `train_identity` (test 동일), `TransactionID`로 조인
- 사기율: 약 3.5%
- 변수: 총 434개. 대부분 익명화 (`V1~V339`, `C1~C14`, `D1~D15`, `M1~M9`, `id_01~id_38`)

### 2.2 목적 진술의 4개 축과 데이터 대응

| 정의의 요소 | 대응 변수 | 평가 |
|---|---|---|
| 거래 맥락 | `TransactionAmt`, `ProductCD`, `card1~6`, `addr`, `dist` | 충분 |
| 기기 맥락 | `DeviceType`, `DeviceInfo`, `id_30~38` (OS/브라우저/해상도) | 충분 |
| 이용자 맥락 | — | **고객 ID 없음.** `card1`+`addr1`+`D1` 조합으로 추정 필요 |
| 행동 맥락 | `C1~C14` (카운팅), `D1~D15` (시간차) | 대리 변수 존재하나 **익명화되어 의미 불명** |
| 예상 피해 규모 | `TransactionAmt` | 대회 호스트 설명상 USD 결제금액. 실제 회수율·부대손실은 알 수 없음 |

### 2.3 명시할 데이터 한계

보고서에 반드시 기술한다.

1. **레이블 정의**: `isFraud`는 대회 설명상 "chargeback이 보고된 거래 + 해당 카드/계정의
   이후 거래 전부"이다. 즉 실제 사기 시점이 아닌 **사후 라벨링**이며, 개별 거래 손실액과
   정확히 대응하지 않는다.

2. **비용 파라미터 부재**: $c_{cb}$, $s_f$, $s_l$, $m$, $L$, $c_{rev}$ 는 데이터에 없다.
   가정으로 도입하고 민감도 분석으로 다룬다 (§3.2).

3. **비용 단위**: `TransactionAmt`는 USD 결제금액이지만 chargeback·오차단·검토·인증 비용은
   데이터에 없다. 따라서 절대 비용 결론 대신 **P0 대비 상대 절감률**과 민감도를 보고한다.

## 3. 정책 설계

### 3.1 정책 사다리

정책을 사전에 확정하지 않고, **한 칸에 하나씩 요소를 더하는 사다리**로 배열해 각 요소의
기여도를 분리 측정한다.

| # | 정책 | 추가되는 것 | 답하는 질문 |
|---|---|---|---|
| P0 | 전건 승인 | — | 무개입 기준선 |
| P1 | 규칙 기반 | 사람의 직관 | ML이 규칙보다 나은가 |
| P2 | 단일 임계값 차단 | 모델 확률 | 모델의 순수 기여 |
| P3 | 비용 기반 임계값 | 비용 구조 | 비용에서 임계값을 유도하면 나아지는가 |
| P4 | + 금액 의존 임계값 | 금액 정보 | 고액/소액 차등이 가치 있나 |
| P5 | + 보류(검토 큐), 예산 $B$ | 사람 검토 | 검토 인력의 한계 가치 |
| P6 | + 추가 인증 | 4번째 행동 | **추가 인증 도입이 정당한가** |

인접 행의 차이가 곧 해당 요소의 기여도가 된다. 개선이 멈추는 지점도 그 자체로 발견이다
(예: P4 ≈ P3이면 "이 데이터에서 금액 의존 임계값은 무가치").

### 3.2 가정에 의존하는 부분의 처리

P5·P6은 데이터에 없는 파라미터에 의존한다. 따라서:

- 비용은 **절대값이 아닌 상대비**로 둔다 (차단 비용 = 1 기준)
- $B$, $s_l - s_f$ 를 넓은 범위에서 변화시키며 **정책 순위 역전점**을 찾는다
- 결론은 "P6을 쓰자"가 아니라 **"$s_l-s_f$가 X 이상일 때 P6이 P5를 이긴다"** 형태의
  조건부 권고로 낸다

> **데이터가 말하는 것과 가정이 말하는 것의 경계를 보고서에서 명시적으로 구분한다.**
> §4(모델)까지는 데이터, §5(정책)의 P5·P6은 가정 위의 도출이다.

## 4. 모델링

### 4.1 요구사항이 통상과 다른 지점

Kaggle 목표는 AUC이며 순위만 맞으면 되지만, 본 연구는 $p$를 기대비용 식에 **숫자로 직접**
넣는다. 따라서 요구사항이 둘로 갈린다:

1. **변별력** — 사기/정상 구분 (PR-AUC, Precision@k)
2. **보정** — 확률값이 실제 빈도와 일치 (ECE, reliability diagram)

2번이 통상 생략되나 본 연구에서는 필수다.

### 4.2 모델 선택

**주력: LightGBM**

- 434개 변수, 대부분 익명 수치형 + 고카디널리티 범주형 (`card1` 1만 개 이상 수준)
- 결측이 블록 단위로 대량 → GBDT는 결측을 분기로 직접 처리, 대치 불필요
- 스케일 불변, 학습이 빨라 정책 실험 전 반복 가능

**대조군: 로지스틱 회귀** — 성능 자랑이 아니라 P1(규칙)과 짝을 이루는 비교 축.
"모델 복잡도 상승이 총비용을 실제로 줄였는가"를 확인.

### 4.3 클래스 불균형 — 가중치를 쓰지 않는다

사기율 3.5%에 통상 `scale_pos_weight`나 오버샘플링을 쓰나, **본 연구에서는 사용하지 않는다.**

**근거 1.** 가중치는 모델이 양성을 과대 예측하도록 학습시켜 원시 출력 확률을 실제 빈도보다
위로 밀 수 있다. 따라서 가중 모델을 쓴다면 별도 보정 후 비교해야 한다.

**근거 2.** 불균형 보정의 목적인 "임계값 조정 효과"를 본 연구에서는 **비용 함수가 명시적으로**
수행한다. 모델 단에서 또 하면 이중 적용이다.

→ 가중치 없는 모델을 기본으로 하되, 가중치 유/무 모델을 각각 보정해 최종 정책 비용까지 비교.
→ 불균형에 따른 의사결정 비용은 정책 단계에서 명시적으로 반영.

### 4.4 캘리브레이션

- **방법**: isotonic regression 우선. Platt(시그모이드)은 형태 가정이 있어 GBDT 출력의
  왜곡을 다 잡지 못함. calib 구간이 10만 건 이상이므로 isotonic 과적합 위험 낮음.
- **분할**: 보정 구간과 학습 구간이 겹치면 안 됨 → 시간순 3분할
- **평가**: reliability diagram, ECE, Brier score
- **금액 구간별 ECE** ← 전체 ECE가 낮아도 고액 구간에서 어긋나면 손실 큰 쪽에서 정책이
  틀린다. 평균 하나로는 보이지 않으므로 반드시 분리 측정.

### 4.5 검증 설계

```
시간축 ──────────────────────────────────────────►
[      train      ][  calib  ][   test (정책 평가)   ]
```

- 하이퍼파라미터: train 내부 시간 기반 CV
- 보정: calib
- 정책 비교: test

**랜덤 split 금지.** 사기 수법은 시간에 따라 변하며, 대회 test set도 train 이후 기간이다.
랜덤 split은 반복 개체와 기간을 섞어 운영 시점보다 낙관적일 수 있다. → §노트북 03에서
같은 학습·평가 건수로 두 방식을 비교하되, 차이를 순수 누수량으로 해석하지 않는다.

**test 과적합 완화**: 여러 정책을 test에서 비교해 최고를 고르면 test에 과적합된다. test를
전반/후반으로 재분할해 앞에서 선택, 뒤에서 확인한다. 드리프트 점검도 겸한다.

### 4.6 피처 엔지니어링 (효과 순)

1. **카드 소유자 추정** — `D1`의 정확한 기준 개체는 공개되지 않았으므로,
   `TransactionDT - D1` 기준일과 `card1`+`addr1`을 결합한 휴리스틱으로 동일 소유자를 근사한다.
   이후 소유자별 거래 횟수·평균 금액·직전
   거래 경과시간 등 행동 피처 생성. **목적 진술의 "이용자 맥락"이 이 부분.**
2. **빈도 인코딩** — 고카디널리티 범주형을 등장 빈도로 치환. 희귀 카드/도메인/기기 신호.
3. **금액 파생** — 소수부(정수 금액 여부), 소유자 평균 대비 비율("평소보다 큰 거래").
4. **집계 피처** — 소유자·기기·이메일 도메인별 통계량.

> **누수 주의**: 집계를 전체 데이터에서 계산하면 미래 정보가 유입된다. 학습 행은 시점 기준
> 누적 집계를 사용하고, 이후 구간에는 train에서 고정한 통계를 적용한다.

## 5. 평가지표

### 5.1 모델 지표 (중간 점검)

| 지표 | 비고 |
|---|---|
| **PR-AUC** | 주 지표. 불균형에서 ROC-AUC는 진음성 과다로 낙관적 |
| ROC-AUC | 병기, 부차적 |
| **Precision@k / Recall@k** | $k$ = 검토 예산. 검토팀의 실제 경험에 대응 |
| **ECE, Brier** | 보정 품질 |
| **금액 구간별 ECE** | 손실 큰 구간의 보정 확인 |

### 5.2 정책 지표 (본론)

**주 지표: 총비용** — 절대값이 아닌 **P0 대비 절감률**로 보고.

**비용 분해** (총비용만으로는 개선의 출처를 알 수 없음):

| 항 | 내용 |
|---|---|
| 사기 손실 | 놓친 사기 금액 |
| 정상 차단 손실 | 막은 정상 거래의 매출·이탈 |
| 검토 비용 | 보류 건수 × 단가 |
| 인증 마찰 | 인증 요구로 인한 이탈 |

**운영 지표**:
- 차단율 / 보류율 / 인증 요구율 (고객이 겪는 마찰)
- **정상 고객 오차단율** — 고객 경험의 직접 지표
- **금액 기준 사기 검출률** — 건수가 아닌 손실액 기준 (건수 재현율과 다르게 나옴)
- 검토 큐 사용률

**안정성 지표**:
- 비용 파라미터 변화에 대한 총비용 곡선
- **정책 순위 역전점** — "$B$ ≥ X 이면 P5 > P4", "$s_l-s_f$ ≥ Y 이면 P6 > P5"
- 기간별(test 전반/후반) 총비용 — 드리프트 하 유지 여부

**공정성**: 세그먼트별(`ProductCD`, `DeviceType`, 지역) 오차단율 격차. 총비용이 낮아도
특정 집단이 체계적으로 과차단되면 채택 불가.

### 5.3 핵심 결과표

보고서 전체의 결론을 담는 단일 표:

```
행: P0 ~ P6
열: 총비용 | P0 대비 절감률 | 4항 분해 | 차단율 | 오차단율 | 금액 검출률
```

### 5.4 주목할 가능성

**AUC와 총비용의 순위가 불일치할 수 있다.** AUC가 낮아도 보정이 잘 된 모델이 총비용에서
이기는 결과가 나온다면, 그것이 본 보고서의 가장 중요한 발견이다 — *무엇을 최적화할지
정하지 않으면 좋은 모델을 골랐다고 말할 수 없다*는 명제의 실증이 되기 때문이다.

## 6. 연구 범위

본 연구는 사기 탐지 **시스템 구축**이 아니라, 그 시스템의 **의사결정 계층을 오프라인에서
설계·검증**하는 것이다.

| 계층 | 본 연구 | 비고 |
|---|---|---|
| 데이터 수집·스트리밍 | ✗ | |
| 피처 서빙 | △ | 오프라인 근사 (시점 기준 누적 집계) |
| 점수 계산 | ✓ | 배치. 실시간 서빙 아님 |
| **결정 정책** | **✓ 본론** | |
| 실행 (차단/인증) | ✗ | |
| 검토 워크플로 | △ | 용량 제약($B$)만 모델링 |
| 피드백·재학습 | ✗ | 아래 참조 |

### 6.1 원리적으로 불가능한 것

**실시간 위험점수** — 결제 승인은 수십~수백 ms 제약이나 본 연구는 배치 예측이다. 서빙
시스템·피처 스토어·지연 측정이 없다. 추론 시간 측정으로 실현 가능성을 *논할* 수는 있으나
검증은 아니다.

**계정·기기 그래프 분석** — 소유자 추정과 그룹 집계까지는 하나, 실무의 연결 분석은 기기-계정
간 링을 찾는 **그래프 탐색**이다. 본 데이터에는 검증할 정답이 없다.

**피드백 루프** — 검토 결과 데이터가 없다. 더 근본적으로, 실제 시스템에서 **차단한 거래는
결과를 관측할 수 없다**(막았으므로 사기 여부를 영영 모름). 이 **선택 편향**이 누적되는
현상은 사기 탐지의 난제이나, 모든 거래에 정답이 붙어 있는 오프라인 데이터로는 재현조차
불가능하다.

### 6.2 마지막 장 구성

위 항목들을 **"제안 정책의 실제 운영 시스템 적용 시 추가 요구사항"** 으로 서술한다:
실시간 점수 계산 / 규칙 기반 탐지 / 위험도별 차등 대응 / 계정·기기·거래 연결 분석 /
사람 검토와 피드백 루프 / 운영 지표 기반 최적화 — 여섯 축.

범위와 가정을 명확히 하는 것은 감점 요인이 아니라 정책 보고서의 기본기이다.

## 7. 구현 구조

### 7.1 원칙

**노트북은 보여주는 곳, 모듈은 정의하는 곳.**

비용 함수와 정책 함수는 여러 노트북에서 반복 사용된다. 노트북 셀에 복붙하면 한쪽에서
파라미터를 고쳤을 때 다른 쪽 결과와 어긋나고, 그 불일치를 발견하지 못한 채 보고서가 나간다.
정책 비교 보고서에서 이는 치명적이므로 **비용·정책·평가는 `src/`에** 둔다.

### 7.2 노트북

| 노트북 | 내용 | 산출 |
|---|---|---|
| `00_data_check` | 4개 파일 병합, 무결성 확인, dtype 최적화 → parquet | `*.parquet` |
| `01_eda_overview` | 시간축, 결측 블록 구조, 카디널리티, 변수군 성격 | 보고서 §2 그림 |
| `02_eda_cost_relevant` | **비용 관점 EDA** (아래 참조) | 정책 설계 근거 |
| `03_validation_design` | 시간 기반 split 정의, 랜덤 split 대비 낙관 편향 실증 | `splits` 고정 |
| `04_features` | 소유자 추정, 인코딩, 파생 변수 | `features.parquet` |
| `05_model` | LGBM+LR 학습, 캘리브레이션, SHAP | `predictions.parquet` |
| `06_policy_comparison` | **P0~P6 비교, 민감도, 공정성** | 핵심 결과표 |

**`02`를 일반 EDA와 분리하는 이유**: 목적 함수가 금액 가중이므로 "사기 *건수* 분포"가 아니라
**"사기 *금액* 분포"** 를 봐야 한다. 구체적으로 — 금액 구간별 사기율 vs 금액 구간별 손실
총액(둘의 순위가 다를 것), 손실 집중도(상위 몇 %가 손실의 몇 %인지), 세그먼트별 사기율 차이.
손실이 소수 고액 거래에 몰려 있다면 P4(금액 의존 임계값)의 근거가 되고, 아니면 P4가 무효할
것이라는 예측이 미리 선다.

**`05`/`06` 분리는 반드시 유지**: 06은 저장된 $p$만 읽으므로 모델 재학습 없이 정책 파라미터를
바꿔가며 빠르게 반복할 수 있다. 민감도 분석을 여러 번 돌릴 것이 확실하므로 실질적으로 중요.

### 7.3 모듈

```
src/frauddetectionreport/
  data.py       # 로딩, 병합, parquet 캐시
  splits.py     # 시간 기반 split 정의 (고정)
  features.py   # 피처 변환 (fit/transform 분리)
  costs.py      # 비용 파라미터 dataclass + 행동별 기대비용
  policy.py     # P0~P6 정책 함수 (공통 인터페이스)
  evaluate.py   # 총비용 집계, Precision@k, 민감도 루프
```

정책들은 **같은 $p$와 같은 비용 함수를 공유**하고 행동 규칙만 다르다:

```
model → p (한 번만 계산, 캘리브레이션 포함)
   ↓
policy(p, amount, params) → action    # 여기만 P0~P6으로 교체
   ↓
cost(action, is_fraud, amount, params) → 총비용
```

`costs.py`의 파라미터는 dataclass 하나로 모은다. 민감도 분석이 이 객체를 바꿔가며 평가를
반복하는 것이므로, 한 곳에 모여 있어야 "이 결과가 어떤 가정 하의 것인지"가 항상 명확하다.

### 7.4 데이터 흐름

```
raw csv → [00] → data/processed/*.parquet
                      ↓
                    [01][02] 탐색 (읽기 전용)
                      ↓
                    [03] → splits 정의
                      ↓
                    [04] → features.parquet
                      ↓
                    [05] → predictions.parquet  (p_calibrated, amount, is_fraud, segment)
                      ↓
                    [06] 정책 실험 (모델 불필요)
```

중간 산출물을 파일로 떨어뜨려 각 노트북의 독립 실행을 보장한다.
